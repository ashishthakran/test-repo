01 The problem

AI agents write more and more code.
Who proves a change is safe to merge?

?

Was every reviewer finding fixed?

?

Did security review run on the exact commit that merged?

?

Can the AI, or an untrusted contributor, bypass a required check?

?

If we switch AI vendor, what must be rebuilt?

Today every team wires AI review by hand, differently — and nothing blocks the merge.
  • Teams already have strong agents. What is missing is a safe, repeatable way to run them inside their own pipeline, with clear rules about when a change may merge.
  • Mature tools each own one part: implementers, reviewers, non-AI CI gates. Nobody ships one declared contract that wires them together and proves, per commit, that every required step passed.
02 How Stagr works

Three layers. Stagr lives only in the middle one.

Declare · initialize · govern
— never execute

The litmus test: "Does this require Stagr to be running while the pipeline executes?" If yes, it does not belong in Stagr. Generated workflows never call back into Stagr.

Not an AI agentNot a runtimeNot a hosted serviceNot a merge botGitHub only today
  • Identity: "a platform-neutral contract + renderer". Stagr writes the wiring; the CI platform runs the work.
  • It is not an agent, not a runtime, not a hosted service or dashboard, and not a merge bot: the generated pipeline never merges.
  • Platform today: GitHub only. GitLab, Azure DevOps and Bitbucket renderers are planned.

CLI today: stagr helpstagr initstagr profilestagr planstagr apply stagr doctor · planned
  • Getting started: (1) install the CLI with pipx (Python 3.10+, not on PyPI yet, pin a release tag such as v0.7.1); (2) create the team's own Stagr GitHub App and store its private key as a secret; (3) add the backend secrets; (4) stagr init writes a full commented template, stagr plan previews new/changed/unchanged/remove with sha256 and writes nothing, stagr apply writes exactly those files; (5) require stagr/governance in a branch ruleset; (6) open pull requests as usual.
  • The shortest working config is 3 lines: version, profile, platform with app_id. The full example above also sets the provider (openai) per stage; shortened here for the slide.
  • Profiles: minimal = code review; standard (default) = code review + security review, security depends on review; custom.
  • Validation before anything is written: schema, dependency cycles, every stage routed, profile minimum stages (V-S01…V-S17). apply owns only files with the # Generated by stagr header and refuses to overwrite files it did not generate.
03 A pull request's journey

Codex reviews. Claude fixes. The gate decides.
A human merges.

Stagr wiring Codex stages Claude fixes Pass / human Blocked
  • Route: deterministic, by file globs. FAST runs the lighter set of stages the team lists; NORMAL runs all. No AI routing.
  • Review and security are blocking stages run by Codex. Backend codex = Codex GitHub App via @codex review; backend codex-api (new in 0.6.0) = Codex on the team's own OpenAI API key, findings posted as one review by the team's Stagr App.
  • Remediation (0.5.0+): Claude Code Action judges each finding, fixes it (one fix(review): commit) or declines with a reply. Bounded by remediation.max_rounds (default 5, range 1–10); then human-merge label and hand-off. Cannot edit .github/** or .agentic/**; never resolves threads.
  • Claude does not implement features from scratch today; an implement stage is roadmap.
  • The generated pipeline never merges. The team makes stagr/governance a required check; a human merges.
04 Why you can trust the gate

"Merge is eligible" only when every
condition holds on this exact commit.

✓

Signed by the team's own App

Each stage publishes a Check Run stagr/stage/<id> authored by the team's Stagr GitHub App. Any other author is rejected.

✓

Bound to the head commit

The payload names headSha. A result for an older commit is ignored.

✓

Every blocking stage passed

Exactly one result per stage, completed, conclusion pass.

✓

Fail-closed

Missing, pending, duplicate or unknown = "Merge is blocked".

Commit statuses are not trusted. Anyone with statuses: write could forge one. A forged status counts for nothing.

Secrets by name

One secrets block (0.7.0). A pasted value is rejected and never printed.

Pinned actions

Every third-party action pinned to a full commit SHA.

No fork automation

Fork PRs never drive automation. Privileged jobs never check out PR code.

Text is data

PR and comment text is untrusted data, never instructions.

Bounded AI

After max_rounds fix rounds: human-merge label, automation pauses.

A human merges

stagr/governance is a required check in a branch ruleset.

  • The JSON payload in each Check Run carries stageId, headSha, state, conclusion. The gate checks the publishing App id, the schema version and the head SHA.
  • Claude's remediation cannot edit .github/** or .agentic/** and never resolves a review thread.
  • Each key reaches only the job that needs it; each workflow has least-privilege permissions.

Answers, never the brain

Residency per application

  • Four planes: Stagr = contract (wiring); CI runners = execution; CodeGuard console = control plane (intent, stories, asks inbox, human verdicts, audit); CodeGuard Brain = knowledge.
  • "Ship answers, never the brain": the Brain Gateway (MCP) is the only door.

10 CodeGuard AI · the target flow

Small agents do the work. An independent judge checks it. Humans decide.

  • Flow: intent → brain-grounded stories → human approves → story split into nanobots (small agents, each owning one task along a frozen contract, coordinating through CodeGuard) → independent judge checks the result against acceptance criteria with evidence (runs the tests, never trusts the agent's "done") → a question for a human pauses the story (asks inbox) → human verdict → Stagr gate → merge → brain learns (post-merge rescan; recurring review findings become proposed conventions).
  • Only the Stagr gate in this picture exists today.
